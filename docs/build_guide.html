PHASE 00

Before you spend anything

~30 minNo parts needed

One measurement decides whether this robot can work at all, and it is not about code. A two-wheeled robot pivoting on the spot sweeps a circle as wide as its body diagonal. If that circle does not fit between the walls, the robot cannot turn around — no amount of tuning fixes it.

The competition passage is one foot: 304.8 mm.

Robot sizeBody diagonalClearanceVerdict
250 × 150 mm292 mm6 mmJams in corners
220 × 115 mm248 mm28 mmTarget — build to this
200 × 110 mm228 mm38 mmFits, but twitchy — short wheelbase

220 × 115 mm is a measured optimum, not a guess. Narrower is not automatically better: a narrower body means a shorter wheelbase, which makes the robot more sensitive to motor mismatch. In simulation, 110 mm wide completed 83% of runs and 115 mm completed 97%.

Measure this today

Put a ruler across your chassis as it stands, nose to tail and tyre-outside to tyre-outside. Most kit builds come out around 250 × 150 mm, and almost all of the excess is in the front ultrasonic bracket hanging off the nose. You need to find about 3 cm of length. Knowing that now changes what you buy.

Two questions worth asking the organisers

  1. What is the actual passage width? The rulebook says 200–400 mm and calls the dimensions "tentative". At 200 mm no standard kit robot can turn at all — that affects every team equally and is worth raising early, in writing.
  2. Are the start and finish gates marked on the floor? It changes nothing in the code, but it is good to know what the robot will see.
PHASE 01

Shopping

Half a day~300 SAR electronics + ~300 SAR tools

Two trips: an electronics shop, then SACO. No practice track — you have the real one, which saves about 120 SAR and a full weekend of cutting foam board.

Which to choose when there is a choice

Scoring is sector points first (§6.1); time only breaks ties (§6.3). So reliability wins the event and weight wins the tie-break. Buy the reliable option, and take the lighter one only where it costs nothing.

Electronics shop (الموجات الإلكترونية, King Fahd St, Khobar)

Do not buy
  • Any second microcontroller — ESP32, Nano, Pi. Rule §2.2, instant disqualification, even fitted and unused.
  • An external memory chip. The Uno's built-in 1 kB EEPROM is ten times what this needs — the junction memory uses 192 bytes.
  • A TCRT5000 line sensor. It was in an earlier version of this design and was removed: its only job was spotting the finish, and a TCRT5000 chatters crossing tape at an angle, which could stop the robot mid-map. Measured with it gone: identical times, every sector line still crossed.
  • Laser distance sensors (VL53L0X/VL53L1X). Modelled, and they measured worse than HC-SR04 here — a wide sonar cone averages a whole square of wall, which is exactly what a wall-follower wants.

SACO (ساكو) — tools

SACO — fasteners

Free weight — about 90 g

Nylon standoffs instead of brass (~35 g), leaving the breadboard off the robot (~30 g, and §2.2 explicitly allows it), cutting wires to length instead of coiling jumper leads (~15 g), green perfboard instead of the white breadboard (~25 g). On a ~600 g robot that is 15%, and it shows up as quicker starts out of every one of Map 3's eight turns.

PHASE 02

Software setup

~45 minLaptop only

  1. Install the Arduino IDE

    Download from arduino.cc/en/software — take IDE 2.x. Install with the default options and let it install the USB drivers when it asks.

  2. Install the CH340 driver (most likely needed)

    Kit Unos are usually clones with a CH340 USB chip rather than the original FTDI. If you plug the board in and no port appears, this is why. Search "CH340 driver" for your operating system, install it, and replug.

    Windows: the port shows up as COM3 or similar. macOS: /dev/cu.wchusbserial.... Linux: /dev/ttyUSB0 — and you may need sudo usermod -aG dialout $USER, then log out and back in.

  3. Select the board

    In the IDE: Tools → Board → Arduino AVR Boards → Arduino Uno, then Tools → Port → whichever port appeared in the previous step.

  4. Prove the toolchain with Blink

    File → Examples → 01.Basics → Blink, then press Upload (the arrow). The board's LED should blink once a second.

    Pass

    Blink uploads and runs. Do not go further until it does — every later problem is easier to diagnose once you know uploading works.

  5. Get the project files

    Download the repository. If you use git:

    terminal
    git clone https://github.com/Muzoka/Robotic-comp.git
cd Robotic-comp

    Otherwise use GitHub's Code → Download ZIP and unzip it.

  6. Optional but recommended: run the simulator

    You need Python 3, pillow, and a C++ compiler (g++ — already present on macOS and Linux; on Windows use WSL). Then:

    terminal
    pip install pillow
python3 tools/geometry_check.py      # can the robot turn in the corridor?
cd sim && python3 run.py --all       # drive all three maps, makes GIFs

    The unusual thing about this project: the simulator runs the real firmware. nav_core.cpp is compiled twice — once by the Arduino IDE onto the Uno, once by g++ into a library the Python simulator drives. What you watch in a simulated run is the behaviour of the code you flash.

PHASE 03

Test the code before you own the parts

~1 hourBrowser only · free

Wokwi is a browser Arduino simulator. It cannot tell you whether the robot navigates a maze — it has no wheels — but it proves the pin map, the I²C gyro, the sonar timing and the whole state machine. This is the cheapest bug-finding available, and it found three real bugs in this project that the maze simulator could not.

  1. New project

    Sign in at wokwi.com (free) → New Project → Arduino Uno.

  2. Paste two files

    Click the diagram.json tab, select all, delete, paste wokwi/diagram.json. Then the sketch.ino tab, select all, delete, paste wokwi/sketch.ino.

    Use wokwi/sketch.ino, not the firmware one

    firmware/MazeRunner/MazeRunner.ino is split across four files and opens with #include "config.h". Paste that one on its own and the build stops with fatal error: config.h: No such file or directory. wokwi/sketch.ino is the same code with all four files already merged, so there is nothing to name and nothing to miss.

  3. Press play, then open the Serial Monitor at 115200

    expected output
    # MazeRunner booting - hold still, calibrating gyro
# gyro OK
# ready. Press GO, or wave a hand in front of the nose.
t_ms,state,dF,dL,dR,head,tgt,encL,encR,pwmL,pwmR,sect
2685,WAIT_START,602,2000,2000,0.0,0.0,0,0,0,0,0
2785,WAIT_START,602,90,90,0.0,0.0,0,0,0,0,0

    602 is the front sensor's default slider (60 cm) and 90 the sides (9 cm). Seeing the right numbers on the right channels is your pin map confirmed.

  4. Check it does nothing on its own

    Leave it alone for ten seconds. It must stay in WAIT_START.

  5. Press the red GO button

    expected
    # GO pressed
6088,COUNTDOWN,602,90,90,...      <- D13 blinks ~3 s
9088,DRIVE,602,90,90,...,200,200  <- both motors forward
9988,STUCK,602,90,90,...,-140,-55 <- expected, see below
Why STUCK is correct here

Wokwi has no wheels, so the encoder counts never rise. From the firmware's point of view the motors are running and the wheels are not turning, which is exactly what "jammed" means — so the watchdog fires after 900 ms. Tap the blue and green buttons to feed it fake encoder ticks, or ignore it. Watch the escape direction alternate (-140,-55 then -55,-140): that is the robot avoiding repeating a failed escape.

Other things worth doing in Wokwi while you have it open:

Do thisShould happen
Drag the front sensor down to 15 cmState goes CREEP → TURN; the IN1/IN2 or IN3/IN4 LEDs swap — it is pivoting
Drag the left sensor up to 100 cm, front clearIt spots a left opening, creeps, then turns left
Drag all three above 60 cmIt keeps going straight — this is the straight-through-a-crossing rule
Check the compile outputRAM comfortably under 2048 bytes. The navigation brain uses 432 bytes, about 21%
PHASE 04

Bench-test each part, one at a time

~2 hoursBefore assembly

Test every subsystem before it is buried inside the robot. Debugging three subsystems at once is how a week disappears. Full sketches are in tools/serial_check.md; here is what each one has to prove.

Wheels off the ground

Put the chassis on a block for anything involving motors. It will drive off the table otherwise.

#TestPass criteria
1Motors All four motions correct — both forward, both back, spin left, spin right — and the wheels stop dead in the pause. Note the lowest PWM at which each wheel actually turns; that is PWM_MIN, usually 50–70.
2Encoders Turn each wheel exactly one revolution by hand; the count rises by 20 (or however many slots your disc has — count them). If it jumps 2–3 per slot you have contact bounce: the disc is rubbing or off-centre in the slot.
3Ultrasonics Hold a flat book at 50, 100, 300 and 1000 mm; each sensor within ~10 mm of a ruler. Then hold the book at 45° — it should report no echo. That is real physics, not a fault, and it is why the firmware treats a missing echo as "far".
4Gyro Three checks: (a) still for 60 s, heading drifts under ±2°; (b) turn 90° by hand against a square, reads 90 ± 3°; (c) turn 90° the other way, reads −90. If the sign is backwards set GYRO_Z_SIGN = -1.0f.
5GO button Steady 1 untouched, 0 while held, back to 1 on release. Always 0 means wrong pin or a short; never 0 means a wire is not making contact.
Try the cross-talk failure deliberately

In the ultrasonic test, remove the delay(60) between sensors and watch the readings go mad. Three sonars firing together hear each other's pings. That is why the firmware fires them one at a time, front / left / front / right — never "ping all three to go faster".

PHASE 05

Mechanical assembly

~4 hoursTarget: 220 × 115 mm

  1. Mount the motors with the axle centred

    The wheel axle should sit halfway along the body. An axle mounted two-thirds of the way back makes the pivot circle bigger for no benefit — and it is usually just a matter of which mounting holes you use. Steel screws and nylock nuts here; this joint carries load. Thread-lock on every one.

  2. Fit the encoder discs and sensors

    The LM393 slot sensor straddles the black slotted disc on the inside of each wheel. Get the disc centred in the slot: if it rubs, it brakes the wheel; too far out and it misses counts. Check by spinning the wheel by hand and watching the sensor's LED flicker evenly.

  3. Bring the body down to size

    This is the step that decides whether the robot works. Everything must sit inside the tyre line and inside the nose — no bracket, sensor, wire loom or battery sticking out past the tyres or off the front.

    The front ultrasonic bracket is almost always the problem. Mount the front sensor flush against the nose, not on an arm. Put the battery on top, never behind the axle — anything behind the axle adds to the tail, and the tail is what sweeps the wall.

    Pass

    Nose to tail ≤ 220 mm. Tyre outside to tyre outside ≤ 115 mm. Measure it, do not estimate it.

  4. Mount the three ultrasonics

    Front one dead ahead in the middle of the nose. Left and right facing exactly 90° out, level, and — this matters — on the wheel-axle line, not ahead of it. That way a gap is seen at the instant the axle draws level with it, which is the moment the robot needs to know. Moving them back from 40 mm ahead to the axle line was worth about 20 percentage points of completion on Map 3 in simulation, and it costs nothing but where you drill.

    Nylon screws here — these boards carry nothing.

  5. Mount the gyro flat, level and rigid

    As close to the middle of the robot as you can. Double-sided foam tape, then a zip tie over the top. If it can wobble, it will report the wobble as turning. Keep it away from the motors and from the motor wires — and twist those wires together to cancel their magnetic field.

  6. Mount the GO button on the back

    On a stiff bracket, so pressing it pushes the robot into the start wall rather than sideways off its line.

  7. Solder the perfboard

    Use the green perfboard, not the white breadboard. A breadboard's spring contacts shake loose, and your robot is a vibrating gearbox bolted to a plastic plate — a run ends the moment one 5 V jumper lifts 0.3 mm. Rule §5.1 prohibits loose components and §11 checks secure mounting; §2.2 names the breadboard as the one part you may remove, which is the rulebook telling you it expects you to solder.

    Lay out: one 5 V rail, one GND rail, three 4-pin headers for the ultrasonics, one 4-pin header for the gyro, two 3-pin headers for the encoders, one 2-pin for the GO button. Everything plugs into that.

Every pin is spoken for. Do not improvise — the firmware assumes exactly this.

Wire in this order

  1. Ground first, everywhere

    Arduino GND, L298N GND, battery −, and every sensor GND all to one rail. If the sonar reads nonsense later, this is the first thing to check.

  2. Power

    power path
                [ SWITCH ]   [ 3A FUSE ]
BATT+  ────────/ ──────────▭────────┬──── L298N +12V
                                    └──── Arduino VIN

BATT−  ─────────────────────────────┬──── L298N GND
                                    ├──── Arduino GND
                                    └──── sensor GND rail

Arduino 5V ─────────────────────────┬──── HC-SR04 ×3  VCC
                                    ├──── MPU-6050    VCC
                                    └──── LM393 ×2    VCC
    • Leave the L298N 5V-EN jumper fitted so the driver powers its own logic.
    • Never join the L298N's 5 V output to the Arduino's 5 V pin.
    • Remove the ENA and ENB jumpers on the L298N. Left fitted, the enable pins are tied high, PWM does nothing, and the robot has exactly one speed: flat out.
    • Never power the motors from USB. It cannot supply the current and you may damage the port.

  3. Noise suppression — do this now, not later

    1000 µF across the battery at the L298N terminals. 100 nF soldered across each motor's own two terminals, at the motor. Skipping these produces symptoms that look exactly like software bugs: random resets, a gyro that drifts only while driving.

  4. Motors

    L298NGoes toControlled by
    OUT1, OUT2RIGHT motorENA (D5), IN1 (D4), IN2 (D7)
    OUT3, OUT4LEFT motorENB (D6), IN3 (D8), IN4 (D11)
    If a wheel spins the wrong way

    Do not swap the wires — set MOTOR_L_SIGN or MOTOR_R_SIGN to -1 in config.h. Swapping wires and signs at the same time is how you lose an afternoon.

  5. Sensors

    Three ultrasonics, gyro on A4/A5, two encoders, GO button. Leave the MPU's AD0 pin unconnected.

  6. Tidy the loom

    Cut every wire to length. Spiral wrap the bundle, zip-tie it down, and check nothing can reach a wheel. Heat-shrink every joint — §5.1 forbids exposed conductor and the inspector will look.

PHASE 07

First power-up

~30 minWheels still off the ground

  1. Before power: continuity check

    Multimeter on continuity. Check battery + to battery − is not shorted, and that GND really is common between the Arduino, the L298N and the sensor rail.

  2. Open the firmware

    In the Arduino IDE, open firmware/MazeRunner/MazeRunner.ino. The other three files (config.h, nav_core.h, nav_core.cpp) appear automatically as tabs because they sit in the same folder. No libraries to install — Wire and EEPROM ship with the IDE.

  3. Upload, then open the Serial Monitor at 115200

    expected
    # MazeRunner booting - hold still, calibrating gyro
# gyro OK
# ready. Press GO, or wave a hand in front of the nose.
t_ms,state,dF,dL,dR,head,tgt,encL,encR,pwmL,pwmR,sect
1240,WAIT_START,1850,1200,1300,0.0,0.0,0,0,0,0,0

    # gyro NOT FOUND means the MPU is answering on address 0x69 instead of 0x68 — that happens when AD0 is tied high. Leave AD0 unconnected.

  4. Leave it alone for ten seconds

    It must stay in WAIT_START and it must not move.

    Why this check exists

    An earlier version of this firmware started its own run about three seconds after power-on, because the sonar filter's history was zero-initialised and the first reading came out as 0 mm — which the start logic read as a hand held up to the nose. The only symptom was the robot driving off while somebody was still placing it. It is fixed and there is a regression test (make test), but ten seconds of watching costs nothing.

  5. Press GO

    Serial prints # GO pressed, the LED blinks a 3-second countdown, then the wheels spin. Hold a book in front of the nose and it should go CREEP → TURN.

    Pass

    All of that works on the block. Now it can go on the floor.

PHASE 08

Measure your robot and calibrate

~1 hourThe step most teams skip

Every threshold in the firmware is derived from the robot's geometry. Put in real measurements and the rest follows automatically; leave the defaults and you are tuning against someone else's robot.

Open firmware/MazeRunner/config.h and set these from a ruler:

ValueMeasureDefault
ROBOT_LENGTH_MMNose to tail, including anything that sticks out220.0
ROBOT_WIDTH_MMTyre outside to tyre outside — not the chassis plate. The tyres are what sweep the circle and what the walls see.115.0
WHEEL_DIAM_MMWheel diameter65.0
US_F_X_MMFront sonar, forward of the axlederived
US_L_Y_MMLeft sonar, left of centrelinederived

PWM_MINLowest PWM at which the wheels actually turn (from Phase 04)55

Then check it still fits
terminal
python3 tools/geometry_check.py

This prints the swept circle for your numbers and tells you the minimum corridor it needs. Run it before you tune anything else — if the geometry does not fit, no gain value will save it.

Then re-run the simulator with your robot

terminal
cd sim
python3 run.py --all --trials 10

If it still completes all three maps, your geometry is fine. If completion drops, the geometry changed something and it is far cheaper to find that here than on the track.

PHASE 09

Tuning on the real track

Several sessionsChange one number at a time

You have the competition track, which is a real advantage — use it methodically rather than doing lap after lap and hoping.

  1. Measure the track before you drive on it

    Passage width, wall height, overall size. If the passage is not 304.8 mm, put the real number in CORRIDOR_MM and re-run geometry_check.py immediately.

  2. One straight corridor first

    Does it drive down the middle without weaving or scraping? If it drifts into a wall, the side sensors are not square. If it weaves, reduce KP_WALL slightly.

  3. One corner

    Does it stop, pivot cleanly, and set off square? A turn that finishes short is usually a loose gyro. A turn that hits the wall mid-pivot means the body is too big — back to Phase 05.

  4. Then whole maps, and record telemetry

    terminal
    python3 tools/telemetry_log.py --port COM3 --out run1.csv

    The real robot prints the same CSV format the simulator does, so you can compare them directly and see where the model and reality diverge.

  5. Adjust speed last

    PWM_CRUISE is the one number that trades time for safety. It ships at 200. Measured across all three maps:

    PWM_CRUISETotal timeCompletedWall contact, degraded hardware
    110182 s100%—
    140147 s100%—
    170128 s100%100 episodes
    200116 s100%none
    230108 s100%none

    200 rather than 230 for a reason you can see in the code: steering is added to cruise and then clamped at 255, so at 200 the robot can still swing 135 counts of left–right difference to save a bad corner; at 230 only 105. That reserve is worth more than eight seconds. If the real track is slipperier than the model, drop to 170 — you lose 12 seconds and every hard correction gets its full authority back.

Discipline

Change one number, run it three times, write down what happened. Changing three things at once and getting a better lap teaches you nothing. Every value lives in config.h, and the simulator reads that same file — so test a change in simulation first. It takes 30 seconds.

Competition day

The bag

Technical inspection (§11)

Then demonstrate the start. That is the strongest thing you can show them.

Starting a run

the whole procedure
1.  Switch on. It calibrates the gyro — KEEP IT STILL for ~3 s.
2.  Place it in the Start Zone, pointing down the first corridor.
3.  Watch it for ten seconds without touching it. It must NOT move.
4.  Press the GO button on the back. Step back.
5.  The LED blinks a 3-second countdown.
6.  It goes. Do not touch it again (§3.4).

Backup start, if the button or its wire fails: hold a hand about 5 cm in front of the nose for a second, then take it away. Same countdown, same run, nothing to plug in. Practise it once so you are not learning it at the table.

Between runs

  • Swap the battery every run, not every third run. A tired battery is the most common cause of a bad second attempt.
  • Wipe the wheels — dust on the tyres makes turns inconsistent.
  • Check the sensors are still square. They get knocked.
  • Put it down flat and still for the gyro calibration. Do not hold it while it boots.

Strategy

  • Points, not speed. One point per sector line all three wheels fully cross (§6.1); time only breaks ties (§6.3).
  • Finishing is not required to score. A robot that keeps moving and keeps crossing lines beats one that solves two maps and jams on the third.
  • Attempts: §3.3 gives 2–3 attempts only if you did not complete the map. Completing slowly beats failing quickly.
  • Do not touch the robot during a run (§3.4, §6.2). If it is stuck, let the judge stop it. Touching it costs the run.
  • Appeals must be filed within 10 minutes (§7.3).

PHASE 12

For other students using this

What transfers, what does not

The repository is at github.com/Muzoka/Robotic-comp. Everything in it is reusable. Three things are worth understanding before you adapt it.

The simulator runs the real firmware

nav_core.cpp contains all the navigation and no Arduino code at all. It is compiled twice: by the Arduino IDE onto the Uno, and by g++ into a shared library that a Python simulator drives. So a behaviour you see in simulation is the behaviour of the code you flash — not a model of it. If you build anything like this, copy that idea before you copy any of the tuning values.

The limit is worth knowing too: the guarantee covers the navigation brain, not the hardware layer. Two of this project's real bugs lived in the hardware layer, where the Python and the C++ had quietly drifted apart.

Your maze is not this maze

The three maps live in sim/maps/build_maps.py as 5×5 grids of P (passage) and X (wall). Change them to yours, re-run the script, and the simulator, the sector lines and the route all follow. It also checks something you should check too: whether your maze has a dead end. If it does, set DEFAULT_MODE to MODE_TREMAUX — the straight-first rule alone can walk out of a crossing that still has road behind it.

The one rule that mattered most

At a junction, go straight if the way ahead is open; only ask the wall-following rule when it is not. One line. On the map with a 4-way crossing it removed both pivots in the crossing — the worst place to turn, because with no wall on either side there is nothing to square up against afterwards. It also lifted the speed ceiling from 170 to 200 and made the left-hand and right-hand rules produce identical routes, so choosing wrong at the start line stopped being able to cost a map.

Things that measured worse than expected

Written down because they are the standard advice and they lost here, on a robot with 20-tick encoders in a 1-foot corridor: trapezoidal turn profiles (78% → 72% completion), yaw-rate damping (78% → 55%), PWM slew limiting (78% → 67%), and laser rangefinders instead of ultrasonics. All are still in the code, switched off, with the measurements beside them. Measure on your own robot before adopting any of it — including this guide.
